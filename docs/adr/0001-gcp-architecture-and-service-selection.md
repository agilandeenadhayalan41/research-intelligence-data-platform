## Decisions

**Architecture principle (lead §30), adopted by this ADR once accepted.** "Object storage and Parquet are the canonical data layer. Analytical engines handle large joins, aggregations, and relationship queries. Operational databases are optional serving projections for workloads that require low-latency indexed access. Consumers interact through stable data APIs and should not depend on the underlying storage technology." D1 and D9 apply the first sentence, D2 the second, D8 the third, and D8 and D9 the fourth.

**Disagreements between the research areas, resolved here:** (1) the authoritative published-release pointer lives in the control plane (D4), not in a Cloud Storage object, because it must commit atomically with SUCCESS, checkpoint and watermark; a create-only publication record in Silver mirrors every pointer move, so the published state of the canonical layer stays readable without PostgreSQL (D1); (2) the SQL binding function is the identity under the default binding and adds project qualification only where needed (D2), which keeps the byte-for-byte evidence chain of [#103]/[#108] while still supporting other datasets; (3) Bronze gets an *unlocked* retention policy plus default soft delete, with no Bucket Lock, versioning or age-based deletion (D1, D12); (4) the cache is in-process now (D8) rather than left open, and DE-30 may move to a shared cache only on its measured trigger; (5) triggers that name a refresh window use 24 h (the operator-stated daily freshness) until the lead signs a window from DE-05's cadence, so no trigger is unmeasurable (D10); (6) Cloud SQL is selected for control state only and not selected for serving, in separate databases with no consumer grants (D4, D8); (7) each ExecutionUnit has exactly one retry owner (D6); (8) until a lease heartbeat exists, Works and deletion task timeouts stay below the 15-minute lease (D5).

### D1 Canonical GCS layout and release manifests

**Decision**: Every GCP environment has two Cloud Storage buckets in the US multi-region (D3), a Bronze (raw landing) bucket and a Silver (canonical) bucket. Immutable canonical Parquet releases in Silver, addressed through their manifest, are the system of record for the modelled canonical tables (lead §3.1, §30). Those tables do not yet hold every source field: the `DEFERRED` and `SOURCE_ONLY` fields of [`field_catalog.py`](../../src/research_platform/canonical/openalex/field_catalog.py) (for example `abstract_inverted_index`, `counts_by_year`, `biblio`, `has_fulltext`) and uncatalogued keys exist only in the raw Bronze bytes. Bronze is therefore retained in full and stays the only complete copy of the acquired dataset until DE-10 [#131] carries the remaining source fields into Silver (abstracts only under D12 (a)); until then lead §3.1 (the full dataset in Parquet) and §4 (the complete representation) stay open under DE-10.

- **Bronze.** Keys stay exactly as [`storage/openalex_layout.py`](../../src/research_platform/storage/openalex_layout.py) builds them: `openalex/<entity>/snapshot_date=YYYY-MM-DD/updated_date=YYYY-MM-DD|none/<asset-id>/source.<ext>`, source bytes never transcoded. Every write goes through `GCSObjectStore.put_if_absent` (create-only generation precondition, SHA-256 verified, `IngestionProvenance` in the `rp_provenance` object metadata, no separate provenance object). OpenAlex source manifests are landed as raw objects; per-run landing manifests (keys, SHA-256, sizes, generations) are create-only objects under `manifests/`. Bucket settings: uniform bucket-level access, public access prevention, soft delete on, an unlocked retention policy (period set in DE-24), no lifecycle delete rule on raw prefixes, Standard class.
- **Silver release.** An immutable, self-contained full snapshot at `openalex/canonical/schema_major=<n>/release_id=<id>/<table>/part-<nnnnn>.parquet`: the 15 `CANONICAL_SCHEMAS` tables plus a new `work_deletion_barriers` table, written create-only with the pinned writer options of [`export.py`](../../src/research_platform/canonical/openalex/export.py). Tombstoned Works and their preserved relationship rows are included. Silver bucket settings: uniform bucket-level access, public access prevention, soft delete at the default window (D12), no retention policy (garbage collection must be able to delete), no lifecycle delete rule, Standard class.
- **Manifest.** `manifest.json` is written last, create-only, and is the only reader entry point (no globbing). It records `release_id` and `parent_release_id`, the schema major version and a per-table schema fingerprint, the build `run_id` and code version, every Bronze input (asset_id, key, SHA-256; deletion assets included), every file (path, SHA-256, bytes, rows), per-table counts and counts by `activity_state`, the barrier count, a content fingerprint and the source-rights reference (D12). It also lists a change set relative to `parent_release_id`: per table, create-only change-set part files holding the inserted, updated and tombstoned rows (for relationship tables, every row of each affected Work), plus new barriers. DE-11 [#132] builds change sets; until then a release carries none. File paths are relative to the release root; consumers resolve a release by its logical `release_id`, and no contract gives them a bucket name or a Cloud Storage URL (D9).
- **Release ID.** Unique, immutable, time-sortable, derived from the build run (not from content), a valid key segment of at most 128 characters (it travels as `publication_version`). A retry of the same build run is an identical replay or a conflict, never an overwrite.
- **Visibility.** A release becomes consumer-visible only when the per-environment published-release pointer in the control plane (D4) moves by compare-and-set, after manifest validation, BigQuery publication (D2) and the quality gates pass. The previous release stays intact for rollback. After the pointer commit, `CONSUMER_PUBLICATION_UNIT` writes a create-only publication record `openalex/canonical/publications/<zero-padded sequence>-<release_id>.json` in Silver: the `release_id`, the manifest path relative to the canonical root, the schema major version, the quality-gate outcome, the publish time and the previous `release_id`. A record never runs ahead of the pointer, and a record missing after a commit is written on retry from the control plane (create-only, so the retry is idempotent). Records are never overwritten and are not deleted while their release is retained; a rollback writes a new record naming the restored release. Readers that do not use the Data Service take the highest sequence as the published release, and a rebuild after loss of the control database restores the pointer from these records, so the published state of the canonical layer does not depend on PostgreSQL (lead §3.1).
- **Retention of releases.** Keep the published release, at least one earlier published release and any pinned release. Unpublished or failed releases are deleted after a grace period, only by a dedicated Silver garbage-collection identity (D11) after it checks the pointer, the release registry and the publication records. A Bronze asset listed by any retained manifest is never deleted, and no Bronze snapshot is deleted while it holds source fields that Silver does not carry (DE-10); the only exception is the D12 (d) takedown procedure. Storage lifecycle is never the OpenAlex deletion mechanism (D12).

**Options considered**: two buckets per environment with manifest-addressed full-snapshot releases (selected); one bucket per environment with `openalex/`, `canonical/` and `manifests/` prefixes and prefix-conditioned IAM; BigQuery native tables as the system of record (what every cloud run effectively did); an open table format such as Iceberg from day one; base-plus-delta releases; a separate `provenance.json` object per raw object. *(PC)* Retention policy, Bucket Lock, soft delete, versioning and lifecycle rules are bucket-wide settings.

**Rationale**: In every cloud run so far BigQuery tables loaded from local files held the only cloud copy (register L03.1-12), which contradicts §3.1. The selected layout fixes that while reusing tested behaviour unchanged: the raw key layout and the create-only `GCSObjectStore` (offline contract tests; [#91] and [#108] smokes), Parquet bytes that are deterministic and whose schema equals the BigQuery contract, and the local stage-then-activate semantics where the old publication survives a failed activation. Two buckets, because Bronze needs never-delete retention while Silver needs count-based garbage collection, and because bucket-level `testIamPermissions` does not evaluate prefix IAM conditions ([`gcs_object_store_smoke.py`](../../scripts/gcs_object_store_smoke.py)), which makes a single prefix-scoped bucket harder to audit. Full snapshots are the simplest model that stays correct for deletions and rebuilds while the real size is unknown; the manifest allows later file reuse without changing readers, and its change set gives downstream projections an incremental input (lead §18: avoid rebuilding downstream representations in full) without changing the release model. The publication records keep §3.1's rule that the canonical dataset does not depend on a serving or query engine, while the compare-and-set stays in the control plane. The barrier table closes a gap found in this research: unknown-work deletion barriers live outside the 15 canonical tables (the in-memory store and the local `deletion_events` table), and `work_publication_decisions.sql` classifies a Work with no target row as INSERT, so a rebuild from today's 15 tables could resurrect a deleted Work.

**Consequences**: The environment contract gains two bucket bindings in place of the single `GCS_BUCKET` (no identifiers committed). DE-06 lifts the `storage.backend=local` refusal only under explicit cloud configuration. DE-07 adds the release publisher, the manifest, the publication-record writer, streamed or partitioned writers (the exporter builds all 15 tables in memory, 5.3–5.4 GiB peak RSS locally at synthetic-100100-works), the barrier table, and moves `lineage_columns` out of `persistence/postgres`; a release must be reproducible from Bronze plus the previous release without BigQuery or PostgreSQL. DE-10 defines when `schema_major` changes. Follow-on acceptance tests: identical replay is a no-op; a conflicting replay raises and keeps the original; a release with a missing part or manifest is never visible; a stale pointer compare-and-set fails; a rebuild from release N equals the incrementally published state; a barrier in release N still blocks a stale ACTIVE Work in N+1 and after a rebuild; the published release is identifiable from Silver alone, and a pointer restored from the publication records equals the control-plane pointer; applying release N+1's change set to release N's published state equals publishing N+1 in full; garbage collection never deletes the published, previous or a pinned release, a publication record of a retained release, or any Bronze input a retained manifest lists. Parquet byte determinism holds only under one PyArrow version, so build dependencies are pinned and a rebuilt release after an upgrade is a new release.

**Not selected**: one bucket with prefix IAM (revisit if DE-04 records a policy that allows only one bucket per environment); BigQuery as the system of record (only an ADR revision amending lead §3.1/§30 reopens it); base-plus-delta releases (revisit after DE-05 if the measured full-release build time exceeds the refresh window or retained-release storage exceeds the DE-26 budget threshold); a separate `provenance.json` object (revisit if serialized provenance reaches 50% of the custom-metadata size limit, or a signed consumer requirement needs provenance listable without reading metadata); rewriting raw keys under `raw/` (only with the single-bucket fallback, through a versioned key migration with replay tests); an open table format now (D10); Bucket Lock, versioning, colder classes and age-based deletion (D12).

**Implemented by**: DE-06 [#127], DE-07 [#128], DE-10 [#131] (remaining source fields), DE-11 [#132] (change sets), DE-32 [#153] (consumer contract for manifests and publication records); inputs from DE-04 [#125] and DE-05 [#126]; pointer and release registry in DE-12 [#133]; bucket controls in DE-24 [#145]; failure and rollback drills in DE-22 [#143].

**Evidence**: [`storage/gcs.py`](../../src/research_platform/storage/gcs.py); [`test_gcs_object_store.py`](../../tests/unit/test_gcs_object_store.py) (`test_create_only_precondition_is_sent`); [`test_canonical_parquet_export.py`](../../tests/unit/test_canonical_parquet_export.py) (`test_arrow_schema_equals_canonical_schema_and_bigquery_contract`, `test_output_bytes_are_deterministic_for_identical_input`); [`e2e/publication.py`](../../src/research_platform/e2e/publication.py) and `test_bounded_e2e_pipeline.py::test_old_publication_survives_failed_candidate`; [#108 Stage 1 landing](../architecture/immutable-local-landing.md#recorded-run-108-stage-1). Canonical Parquet in Cloud Storage, its footprint and a load from it: not yet measured (none exists).

### D2 BigQuery native tables as the authoritative analytical Silver and Gold

**Decision**: BigQuery native tables (partitioned and clustered as in `sql/bigquery/openalex/ddl/`) in US multi-region datasets are the authoritative *analytical* Silver and the Gold layer. They are derived and rebuildable: built only from validated Silver releases by BigQuery load jobs over Cloud Storage objects that a release manifest lists (never local files, never wildcards) into staging, followed by the existing publication SQL (`work_publication_decisions`, then `merge_works` and `REPLACE_BY_WORK_ID`). An incremental publication loads only the change-set files of the release (lead §18; change sets from DE-11, incremental publication in DE-14); a first load, a rebuild, or any publication before change sets exist loads every file of one release. A rebuild loads one release into an empty dataset and must reconcile with that release's manifest. BigQuery never writes canonical Parquet and is never an input to a canonical build. A publication ledger records which `release_id` each dataset holds; re-publishing a release is idempotent and a conflicting re-publication is refused. Silver and Gold datasets have no default table or partition expiration in any environment; only scratch, staging and ephemeral test datasets expire.

**Dataset binding.** The authoritative SQL keeps the logical dataset token `openalex`. One binding function (policy in DE-13, applied by the D7 runner) maps logical tokens to physical datasets and pins the job location to US. Under the default binding (one project per environment, dataset `openalex`, job project equal to data project) it is the identity, so files are submitted byte for byte as in [#103]/[#108]. It renders `<project>.<dataset>` qualification only when the job project differs from the data project, for ephemeral test datasets with the existing `r_<32 hex>` suffix, or for added logical datasets (scratch, consumer-published). It tokenizes (no string replace), refuses unknown tokens and leaves none unrendered.

**Options considered**: native tables loaded from releases (selected); BigQuery external tables over Silver Parquet; BigLake tables; Iceberg tables; native tables as the system of record. For naming: the literal dataset with project-only isolation (the interim state); a logical token plus one binding function (selected); unqualified table names plus the job's default dataset.

**Rationale**: BigQuery native is the only engine ever run in the cloud: all 15 DDL statements, MERGE/REPLACE publication, a failure-injected transaction rollback, 9 Gold SELECTs, 12 quality files and 11 query patterns ran in GCP_SANDBOX ([#103]; [#108] Stages 1–2, 95/95 checks each) and in the personal DEV/QA projects ([#108] Stage 3, 95/95). The measured partition pruning, the leading-column clustering effect observed at ~100k (0.157 of the estimate; cause not isolated) and the transactional REPLACE depend on native tables; *(PC)* external tables support no DML and no clustering, so the publication SQL could not target them. Lead §19 and §22 say to test Cloud Storage + BigQuery first. The binding rule reconciles two research proposals (full qualification everywhere versus identity binding): qualification is added only where it is needed, so evidence continuity is kept and every one of the 61 files is touched only by a tested function.

**Consequences**: A load from Cloud Storage was never exercised (all loads so far came from local files; the 19 Parquet loads in #103 were not billed). DE-14 adds the ledger and a rebuild-from-release test; reconciliation excludes `run_id` and `processed_at`, because `merge_works.sql` touches them on IDENTICAL while the canonical stores do not, unless DE-14 aligns that behaviour. DE-14 replaces staging tables on each load, so staged copies do not accumulate under the staging expiration ([Cost model](#cost-model)). The publication SQL compares staged rows with the target tables (`work_publication_decisions.sql` reads the pre-MERGE `openalex.works`), so the same files apply to a change set or a full release; DE-14 tests both paths. DE-13 creates datasets with location US, forbids default expirations on Silver and Gold, and changes static validation so authoritative SQL contains only logical tokens. Neither `BigQueryWarehouse` nor the sandbox runner pins a job location today. *(PC)* Load-job limits on source URIs and file counts constrain part sizing (DE-07, DE-14). Two stored copies (Parquet and native) are accepted and costed separately ([Cost model](#cost-model)).

**Not selected**: external tables as the primary analytical layer (revisit in DE-35 if DE-18 measures loading plus publishing one release above the refresh window, native storage becomes the largest cost line for a release, or a named consumer must query a non-loaded release at least monthly; then compare the 11 patterns on both at the same scale); BigLake and Iceberg tables (D10); unqualified names plus the default dataset (revisit if DE-19 adopts a tool whose compiler owns qualification); capacity reservations (D13).

**Implemented by**: DE-13 [#134], DE-14 [#135], DE-16 [#137], DE-17 [#138], DE-18 [#139]; releases from DE-07 [#128]; change sets from DE-11 [#132].

**Evidence**: [recorded runs #103, #108 Stages 1–3](../architecture/bigquery-analytical-models.md#recorded-run-103); [`analytics/bigquery/contracts.py`](../../src/research_platform/analytics/bigquery/contracts.py) (`render_create_table_ddl(..., dataset=...)`) and `test_bigquery_analytical_contracts.py::test_ddl_render_matches_on_disk`; [`warehouse/bigquery.py`](../../src/research_platform/warehouse/bigquery.py). Behaviour at real or representative scale: not yet measured.

### D3 Data location and environment isolation

**Decision**: Every Cloud Storage bucket and BigQuery dataset in every environment is in the **US multi-region** (user decision, 2026-10-14). Regional services (Cloud Run jobs and service, Cloud Workflows, Cloud Scheduler, Artifact Registry, the Cloud SQL control instance and any later cache) run in one US region co-located with the data, chosen in DE-04/DE-24. There are no cross-location loads, joins or copies, and every BigQuery job pins location US. There is one enterprise-managed GCP project per environment (GCP_SANDBOX, DEV, QA, PROD); LOCAL stays a reference rung, and promotion stays adjacent-only through `can_promote` with no override. DE-04 obtains GCP_SANDBOX, DEV and QA; PROD is requested only when DE-27 can show the QA→PROD gate. Each project has its own budget, buckets, datasets and identities and no cross-environment grants, and each environment acquires and builds its own releases. Operator-owned and personal projects never count as these environments, and their evidence keeps its labels. Ingestion reaches the AWS-hosted public source (anonymous HTTPS to `openalex.s3.amazonaws.com`; no AWS account or credentials; the program's only AWS contact) only through an egress path DE-24 approves with an allow test and a deny test. Recovery is by rebuild: BigQuery from retained Silver releases, Silver from Bronze or the public source, and the published-release pointer from the Silver publication records (D1); RPO and RTO are open inputs.

**Options considered**: US multi-region (selected); a single US region such as `us-central1` (the [#91] bucket was regional); dual-region Cloud Storage with a US dataset; a non-US location; one shared project with per-environment datasets and buckets; keeping the operator-owned and personal projects.

**Rationale**: The user decided US multi-region. It matches the recorded BigQuery runs: the [#103] dataset was operator-created in US with the `bq mk --location=US` command that the #103 script's docstring documents (the script itself creates no dataset and pins no location). It also matches the [#108] Stage 3 buckets (US); the GCP_SANDBOX smoke bucket of [#91] was regional (`us-central1`). No residency constraint is recorded. *(PC)* One location satisfies BigQuery's co-location rule for loads from Cloud Storage and avoids cross-location joins; multi-region storage is geo-redundant within the US. Durability comes from rebuildability, which §3.1 requires anyway, not from dual-region replication without a stated RPO (§22). Project per environment matches the readiness model; *(PC)* projects scope budgets, quotas, IAM and audit logs; and [#108] Stage 3 showed project isolation working (the DEV identity was refused the QA dataset, in personal projects).

**Consequences**: *(PC)* Bucket and dataset locations are fixed at creation, so the choice is effectively permanent per resource; *(PC)* the US multi-region is not a compute location; *(PC)* transfer between a regional service and multi-region data may be charged, which DE-24 confirms for the chosen region. The org-policy resource-location constraint must allow US. Always-on components multiply by four environments, so non-PROD environments prefer scale-to-zero services. Personal billing accounts already hit a project-link quota in [#108] Stage 3, so DE-04 depends on the enterprise organization.

**Not selected**: single-region or dual-region data (revisit if an org-policy location constraint or a recorded residency requirement excludes the US multi-region, DE-24 records an RPO only dual-region meets, or DE-26 billing export shows inter-location transfer above 5% of an environment's monthly bill for two consecutive months); a non-US location (revisit when a named consumer or legal requirement is recorded); one shared project (revisit only if DE-13 has merged parametrized datasets and DE-04 records that separate non-PROD projects are unavailable; never for PROD); operator-owned or personal projects as environments (never; DE-04 records a blocker and stops).

**Implemented by**: DE-04 [#125], DE-24 [#145], DE-13 [#134], DE-27 [#148].

**Evidence**: [`bigquery_sandbox_103.py`](../../scripts/bigquery_sandbox_103.py) (docstring `bq mk --location=US`; requires an operator-created empty dataset); [#108 Stage 3 QA](../architecture/bigquery-analytical-models.md#recorded-run-108-stage-3-qa); [`readiness/validation.py`](../../src/research_platform/readiness/validation.py) (`can_promote`); [`sources/openalex/connector.py`](../../src/research_platform/sources/openalex/connector.py). Enterprise projects, egress and DR: not yet measured.

### D4 Durable control plane: Cloud SQL for PostgreSQL, control state only

**Decision**: Cloud SQL for PostgreSQL is the selected production engine for pipeline control state: one dedicated control-only database per enterprise environment (whether DEV and QA share one non-PROD instance is a DE-04 input), in the D3 US region with US backups, adopted only after DE-12 passes the gates below.

- **Scope:** pipeline runs; source-file registration and claim/lease; an append-only attempt and audit history; checkpoints; publish IDs; the per-environment published-release pointer (mirrored by the Silver publication records, D1); per-entity watermarks; the run-level single-active-run lease; the SINGLE_WRITER publication lock.
- **Exclusions:** no canonical rows (canonical data stays in Silver; `PostgresCanonicalStore` stays local-only); no serving tables (#23 stays `not_planned`; `serving.work_lookup` is never applied there); no consumer or Data Service identity is granted access. The DE issues' stop rule "No mandatory PostgreSQL/AlloyDB" and DE-35's Cloud SQL/AlloyDB clause govern *serving projections*, not this control store. The lead architect's approval of this ADR confirms that reading; if the lead rules otherwise, the Firestore fallback below becomes the selection.
- **Access:** only through the existing `ControlStore` contract, by evolving `PostgresControlStore` and `sql/control/` with versioned forward-only migrations applied by a dedicated control-schema migration Cloud Run Job, which has its own runtime identity, is the only identity with DDL on the control database and connects over the approved private path (the deploy workflow starts it; the deploy identity has no database login); IAM database authentication and DML-only grants for the runtime identity; private connectivity (DE-24); no passwords or connection strings in the repository.
- **Data plane split:** record-grain lineage (`record_provenance`) and the per-Work deletion audit (`deletion_events`) move to the data plane (the lineage columns already on every canonical row plus release-scoped, append-only audit), so the database stays at run/file grain.
- **Publication protocol:** at-least-once execution, exactly-once visibility. Workers write attempt-scoped immutable outputs and a manifest checksum; one control transaction then re-checks the claim token against the database server clock and commits SUCCESS, the checkpoint, the watermark and the pointer compare-and-set together. This is a documented `ControlStore` contract-version change from the local rule that SUCCESS commits with canonical rows; the local memory and PostgreSQL paths keep today's behaviour for offline tests.
- **Fallback:** Firestore (Native mode, dedicated database, US multi-region) behind the same contract and conformance suite.

**Options considered**: Cloud SQL for PostgreSQL (selected); Firestore; BigQuery tables; Cloud Storage objects with generation preconditions; Spanner; AlloyDB; orchestrator-internal state; self-managed PostgreSQL.

**Rationale**: The control contract proven locally is relational and lock-based: row-locked claims (`SELECT ... FOR UPDATE`), a partial unique index on the active claim token, lifecycle CHECK constraints, foreign keys and multi-row transactions. Only the PostgreSQL engines reuse `PostgresControlStore`, `sql/control/` and the 16 opt-in PostgreSQL integration tests without a rewrite, and Cloud SQL is the smallest managed one (*(PC)* AlloyDB is sized for OLTP/HTAP and is the named #23 serving candidate; Spanner's provisioned floor far exceeds run/file-grain state). *(PC)* Cloud Storage preconditions are single-object, so they cannot commit SUCCESS, checkpoint, watermark and pointer together, which is why the pointer lives here. *(PC)* BigQuery has no row locks, and each transition would be a billed job (the 10 MiB per-table floor dominated #108 billing; #118 cold BigQuery queries took seconds); control writes also stay off `Warehouse.query`. TaskMessage is capped at 8,192 bytes, so control state cannot live in the orchestrator. The main tension is a standing instance per environment against §22, which the Firestore trigger and gate C9 address.

**Consequences**: `apply_ingestion_schema` is split into a control-only path and a local canonical path. New entities (attempt/audit log, checkpoints, pointer, watermarks, locks) feed register rows L18-01, L18-14 and L03.1-09 and the `PUBLICATION_CONCURRENCY` domain. Lease checks move from caller-supplied timestamps to the server clock, and a `renew_lease` heartbeat is added (D5 covers the interim). Two adapter divergences found in research are fixed by the conformance suite: the `record_provenance` idempotency key, and which statuses `create_pipeline_run` accepts. psycopg and a Cloud SQL connector become production dependencies; DE-27 adds an opt-in, gated PostgreSQL conformance job, because CI runs none today. The readiness model has no control-plane domain: DE-12 adds one or records evidence under `RECOVERY` and `PUBLICATION_CONCURRENCY`, without changing promotion rules. **DE-12 control gates:** C1 a backend-parametrized `ControlStore` conformance suite passes on memory, local PostgreSQL and a Cloud SQL test database; C2 N parallel tasks racing for one asset produce exactly one winner; C3 lease expiry on the server clock with a heartbeat or a TTL above the maximum task duration, so a zombie worker cannot commit or move the pointer; C4 replay and kill tests after landing, after staging, and after commit but before acknowledgement leave identical state and the last published release unchanged; C5 the schema applied in Cloud SQL holds only control tables; C6 negative least-privilege tests (DDL only for the migrator, none for the runtime; no connection for the Data Service or the deploy identity; no password auth); C7 private connectivity allowed on the approved path and denied elsewhere; C8 a backup and point-in-time-restore rehearsal meets the owner's RPO/RTO; C9 measured instance-hours, storage and operations per bounded run, compared with the Firestore model at the same operation counts; C10 evidence only from approved enterprise environments.

**Not selected**: Firestore (named fallback; revisit on any of: the lead rules that the stop rule covers control state; DE-24 cannot approve private connectivity to Cloud SQL; C1–C4 fail and cannot be fixed in the adapter; after 3 months in enterprise DEV/QA the measured instance cost exceeds the budget owner's threshold while average CPU stays below 5%); BigQuery tables (revisit if DE-21 guarantees a single writer per asset and a DE-22 overlap test shows zero concurrent-DML conflicts and p95 commit latency below 10% of the lease TTL); Cloud Storage objects as mutable control state or pointer (revisit if the control contract shrinks to single-key state, or both Cloud SQL and Firestore fail a DE-12 gate); Spanner (revisit if, at planned parallelism, Cloud SQL p95 claim/commit exceeds 1 s or lock-wait timeouts exceed 0.1% of claims, or the owner sets a cross-region control RTO under 1 minute); AlloyDB for control (revisit if Cloud SQL fails that latency/throughput gate while PostgreSQL compatibility must be kept; control and serving stay separate databases even then); orchestrator-internal state (revisit if an orchestrator with durable compare-and-set state passes C1–C4); self-managed PostgreSQL (never on GKE; a VM only if policy disallows both Cloud SQL and Firestore).

**Implemented by**: DE-12 [#133]; with DE-22 [#143], DE-23 [#144], DE-24 [#145], DE-27 [#148]; record-grain lineage in DE-16 [#137] and DE-25 [#146].

**Evidence**: [`control/store.py`](../../src/research_platform/control/store.py); [`persistence/postgres/control_store.py`](../../src/research_platform/persistence/postgres/control_store.py); [`sql/control/001_pipeline_control.sql`](../../sql/control/001_pipeline_control.sql); [`test_postgres_ingestion.py`](../../tests/integration/test_postgres_ingestion.py) (`test_concurrent_connections_cannot_both_claim`; opt-in, not run in CI, no dated pass recorded); [pipeline control](../architecture/pipeline-control.md#write--transaction-boundary). ### D5 Ingestion runtime: Cloud Run Jobs

**Decision**: The nine physical Step-20 ExecutionUnits run as Cloud Run Jobs: one container image of the existing package, deployed only by immutable digest; one Cloud Run Job per ExecutionUnit with its own resources, timeout, task count and runtime identity (D11); one typed unit-runner entry point (`src/research_platform/jobs/`, new in DE-20).

- `WORKS_INGEST_UNIT` and `DELETION_UNIT` fan out one task per bounded asset, at most 10,000 per execution (`MAX_BACKFILL_FILES_PER_RUN`); each task calls `ingest_works_asset` or `ingest_deletion_asset` exactly once. `DISCOVERY_UNIT` is a single task that writes the bounded asset list to object storage and passes only its `object_key_ref`. The BigQuery-bearing units are single-task jobs that call the D7 runner. `CONSUMER_PUBLICATION_UNIT` is a single-task, single-writer activation.
- **Exit and outcome contract:** a retryable transient failure exits non-zero; a non-retryable outcome (any `FailureCategory` outside the unit's retryable categories, for example `QUALITY_HARD_GATE`, `CANONICAL_CONFLICT`, `RESTORE_REQUIRED` or `PUBLICATION_CONFLICT`) is recorded in the control store and reported to the orchestrator without triggering any platform retry; on SIGTERM the runner cancels in-flight BigQuery jobs and leaves claims recoverable.
- **Lease and timeout invariant:** until DE-12 adds a heartbeat, a Works or deletion task timeout is set below the fixed 15-minute claim lease; afterwards each attempt either finishes inside its lease or renews it.

**Options considered**: Cloud Run Jobs (selected); Cloud Batch; Dataflow (Apache Beam); GKE with KubernetesPodOperator; Cloud Functions.

**Rationale**: The compute is per-asset streaming Python (fetch, hash, decode, map) plus BigQuery SQL that runs server-side; nothing needs a cluster, a distributed shuffle or a Beam rewrite (§2, §28, §29). Cloud Run Jobs runs the tested Step 12–19 functions without a rewrite (DE-06/DE-20 still have to lift their `storage.backend=local` guards under explicit cloud configuration), as #25 requires, with per-job identity, resources and timeouts and task parallelism up to the 10,000-file contract ceiling, and it costs nothing while idle *(PC)*. Unit safety (create-only landing, `ALREADY_SUCCESS` replay, claim/lease, hard gates) already lives in code, which meets the *(PC)* rule that job tasks must be idempotent.

**Consequences**: *(PC)* The container filesystem is in memory. Raw landing writes a temporary file the size of the source file, and the only memory data are local (5.3–5.4 GiB peak RSS; WSL, 4 cores, 7.7 GiB RAM, synthetic-100100-works), so DE-20 must size memory and scratch by measurement (with DE-07/DE-09 streaming writes or a volume mount). The `storage.backend != local` refusals are lifted only under explicit cloud configuration. The memory control backend loses state when the process exits, so DE-12 is a prerequisite. Egress to the OpenAlex host needs DE-24 approval. No Dockerfile, image or job definition is tracked today; job definitions carry symbolic placeholders only, and a DE-20 test rejects literal project IDs, bucket names and identity names.

**Not selected**: Cloud Batch (revisit if DE-20 or DE-18 measurements at the DE-05 representative asset size show a unit attempt needing more than the Cloud Run per-attempt timeout ceiling, peak memory plus scratch above 75% of the largest Cloud Run instance memory, local SSD, persistent disk or GPUs, or the cost owner requiring Spot-VM economics for a full-snapshot backfill); Dataflow, Spark/Dataproc, GKE and Cloud Functions (D10).

**Implemented by**: DE-20 [#141]; DE-22 [#143]; DE-27 [#148]; DE-12 [#133] as prerequisite.

**Evidence**: [`orchestration/execution.py`](../../src/research_platform/orchestration/execution.py) (9 units); [`ingestion/pipeline.py`](../../src/research_platform/ingestion/pipeline.py) (`DEFAULT_LEASE`, temporary-file landing, local-only guard); `test_orchestration_contracts.py::test_works_ingest_unit_single_physical_invocation`; [local generation timings](../architecture/bigquery-analytical-models.md#required-future-real-bigquery-validation). Any Cloud Run duration, CPU or memory: not yet measured.

### D6 Orchestration: Cloud Workflows triggered by Cloud Scheduler

**Decision**: Cloud Workflows sequences the nine units. Cloud Scheduler starts `SCHEDULED_INCREMENTAL` runs under its own identity; `MANUAL` and `BACKFILL` runs are started through the API by an authorized identity. An offline adapter generates the workflow definition from `build_openalex_works_graph()`, `EXECUTION_UNIT_RETRY_POLICIES` and new per-unit timeouts; it is checked in and tested, and contains no business logic or SQL text. Only TaskMessage-bounded identifiers (at most 8,192 bytes) cross unit boundaries, and a failed gate stops the run before `PUBLISH_SUCCESS`.

- **Retry ownership:** exactly one retry owner per unit; total attempts never exceed the unit's `max_attempts` (at most 5); non-retryable categories are never retried. Per-asset fan-out units (`WORKS_INGEST_UNIT`, `DELETION_UNIT`) are retried by Cloud Run task retries (at most `max_attempts` − 1 per task) and not by the workflow step, so one failed asset does not re-run the execution; single-task units are retried by the workflow step, and their Cloud Run task retries are 0. A workflow step timeout is at least attempts × (task timeout + retry delay).
- **Overlap and duplicates:** *(PC)* Workflows has no max-active-runs setting, so a run-level single-active-run lease in the control plane (D4) and single-writer consumer activation prevent overlap; run identity is keyed to the schedule slot, so a duplicate *(PC: at-least-once)* Scheduler delivery is idempotent.
- **Scheduler neutrality:** the Step-20 contracts keep importing no Airflow module, so Cloud Composer remains a drop-in alternative that needs only a new adapter.
- **Sign-off condition:** if DE-04 confirms an enterprise-operated, shared Cloud Composer environment this program may use, the lead architect may select Composer instead, invoking the same Cloud Run Jobs; D5 and DE-22 stay unchanged. This ADR is the "approved alternate" to managed Airflow that DE-21 allows.

**Options considered**: Cloud Workflows + Cloud Scheduler (selected); Cloud Composer (managed Airflow) invoking the same jobs; Cloud Scheduler + Cloud Run Jobs with no workflow engine; business code inside orchestrator workers.

**Rationale**: The workload is a strict linear chain of nine units with two hard gates and no branching, and every safety property (single ingest invocation, replay, create-only landing, claim/lease, gates, publication scope) lives in platform code. The orchestrator therefore needs only sequencing, stop-on-gate-failure, bounded category-predicate retries, timeouts, a schedule trigger, small parameters and failure alerts, which Workflows provides with no always-on environment *(PC)*. Composer's always-on environment, image upgrades and metadata database *(PC)* are disproportionate for one pipeline (judged qualitatively; nothing is measured and no prices are used). [#25] and [#33] asked for Composer compatibility, not adoption, and compatibility is preserved. The definition can be checked offline with the already-pinned PyYAML, while Airflow DAG tests would add apache-airflow.

**Consequences**: The contracts gain per-unit timeouts (none exist today). *(PC)* There is no local Workflows emulator, so behavioural evidence needs an approved sandbox execution (DE-21) and failure injection (DE-22), never default CI. Fan-out stays inside Cloud Run Jobs, never in workflow iterations *(PC: variable and step limits)*. DE-21 updates the Airflow-shaped wording without changing evidence levels: the mapping in [orchestration.md](../architecture/orchestration.md#airflow--composer-compatibility-future), the registry gap text and `test_environment_readiness.py::test_orchestration_runtime_gap_surfaced`, the proposed diagram, and DE-21's planned `dags/` files (the `dags/` placeholder becomes a retire candidate). `ORCHESTRATION` stays `CONTRACT_DEFINED`/`CLOUD_UNVERIFIED`.

**Not selected**: Cloud Composer (revisit if DE-04 confirms a shared enterprise Composer environment, the program needs more than 3 independently scheduled pipelines with cross-pipeline dependencies, DE-33 runbooks record more than 2 manual re-entries or backfills a month that need task-level clear/rerun or catchup, or a documented Workflows limit makes a DE-21 or DE-22 acceptance test fail); Scheduler + Cloud Run only (revisit if DE-21 is descoped or the physical plan shrinks to 2 or fewer units); business code in orchestrator workers (revisit only if DE-19 selects a tool with a governed invocation API and a DE-19 test demonstrates byte caps and gate evaluation through it).

**Implemented by**: DE-21 [#142]; DE-22 [#143]; run lease in DE-12 [#133]; alerts in DE-26 [#147]; runbooks in DE-33 [#154].

**Evidence**: [`orchestration/graph.py`](../../src/research_platform/orchestration/graph.py); [`orchestration/retry.py`](../../src/research_platform/orchestration/retry.py); [`orchestration/models.py`](../../src/research_platform/orchestration/models.py); `test_orchestration_contracts.py::test_no_airflow_dependency_imported` and `::test_retry_policies_are_bounded`. Any Workflows execution: not yet measured.

### D8 Serving: one Cloud Run service with a release-aware in-process cache

**Decision**: The Data Service HTTP API runs as **one Cloud Run service**: a thin authenticated HTTP adapter (new `src/research_platform/api/`, DE-28) over the existing `DataService` and `ConsumerDataRepository` contracts (`data-service-contract-v1`, unchanged), backed by a new read-only BigQuery repository that reads only published, release-pinned Gold or serving objects. It offers domain endpoints only: no `/sql`, no free-form query and no SQL-text parameter. It uses IAM-authenticated invocation, internal ingress by default, a dedicated read-only runtime identity (D11), bounded row limits, request rate limits, `maximum_bytes_billed` on every BigQuery read and safe error envelopes (401/403/404/429), and runs in the D3 US region, only in DE-04-approved projects.

- **Cache:** in-process and per instance, hardened from the [#118] `TtlLruCache`: the release id in every key, thread safety, NOT_FOUND cached only within one release, invalidation on publication and deletion, a TTL no longer than the 24 h freshness requirement, hit/miss metrics. Minimum instances and prewarming of hot keys are the levers intended to keep the miss share under 5% (unproven: [#118] prewarmed all 1,000 keys of a synthetic working set; DE-30 measures the real one).
- **Read path:** `work_metadata_lookup` reads the `research_discovery` model compute-on-read over the published, release-pinned tables (`COMPUTE_ON_READ` today). DE-30 [#151] measures its miss path end to end. If the measured miss p95 exceeds the miss-path latency target that the API product owner sets, or the bytes per miss exceed the DE-26 cost threshold, DE-17 [#138] materializes a release-pinned serving table under the Gold registry rule that `MATERIALIZED` requires `MEASURED` evidence.
- **Routing (lead §14, §15):** static per capability, taken from its placement in [`config/query-patterns/openalex.yaml`](../../config/query-patterns/openalex.yaml): `BIGQUERY_PLUS_CACHE` capabilities go through the cache, `BIGQUERY_ANALYTICAL` ones to BigQuery, and `MATERIALIZED_AGGREGATE` ones read compute-on-read Gold until DE-17 materializes them under the same rule; `UNRESOLVED` capabilities are not exposed. No runtime query router is built until a second backend is approved (#23 reopened or DE-35). Each endpoint documents its latency class, freshness (release id and publish time), pagination, limits, one-release-per-response consistency, and that it is synchronous.
- **No operational store:** Cloud SQL, AlloyDB and other operational stores are not selected for serving; #23 stays closed `not_planned`, and the #112 projection stays an unapproved, undeployed prototype.
- **Strength:** selected, not locked. DE-30 re-measures misses end to end through the deployed path before the cache decision is confirmed.

**Options considered**: for the runtime, a Cloud Run service (selected), Cloud Run functions, GKE; for the cache, in-process (selected) or Memorystore; for the store, a Cloud SQL or AlloyDB lookup projection (the #112 prototype), or BigQuery alone with no cache.

**Rationale**: BigQuery alone misses the operator-stated 200 ms end-to-end p95: client p95 1,100–1,506 ms in GCP_SANDBOX on synthetic data (server-side p95 196–598 ms, which excludes the client round trip) ([#108] Stages 1–2; [#23 comment](https://github.com/agilandeenadhayalan41/research-intelligence-data-platform/issues/23#issuecomment-6130919648)). [#118] shows that the cache governs: a hit costs microseconds and a miss 2.4–3.1 s, so the p95 is met only if fewer than 5% of requests miss; the cold runs missed and the prewarmed runs met. A Cloud Run service hosts all five capabilities and one cache in one container, with warmth levers set by configuration *(PC)*, and shares its container path with D5. A shared cache removes only fragmentation and restart misses, not long-tail misses, and adds a hop that was never measured and that the [#23 closing criteria](https://github.com/agilandeenadhayalan41/research-intelligence-data-platform/issues/23#issuecomment-6139894312) treat as a failure condition. §22 and §29 add an operational store only on measured failure. **Limit of the evidence:** #118 timed only the works-table lookup SQL (`queries/doi_work_lookup.sql`, `openalex_work_id_lookup.sql`) with a dry run per miss, while `work_metadata_lookup` needs the `research_discovery` read (author, topic and institution arrays over four tables, `COMPUTE_ON_READ`), so the real miss path is unmeasured and probably heavier.

**Consequences**: DE-28 adds an HTTP framework dependency (chosen there), a BigQuery-backed repository and an image. DE-30 hardens the measurement-grade cache (today it has no lock, a mutable `last_was_hit`, no release in its keys, NOT_FOUND cached for the whole TTL and a clear-all invalidation) and measures end-to-end p95, hit and miss share, concurrency and bytes per miss through Cloud Run; it also measures prewarm bytes per instance and per publication, because every instance re-warms after each publication, instance start and TTL expiry. Minimum instances are an always-on cost driver. BigQuery under concurrent misses and lookup clustering are unmeasured. DE-29 adds ISSN/eISSN, source and publisher lookups through the same contracts; `issn-source-lookup` stays `UNRESOLVED`. The lookups stay `BIGQUERY_PLUS_CACHE` / `ASSUMED`, and `OPERATIONAL_STORE_OPTIONAL` stays `OPTIONAL_NOT_REQUIRED` and non-blocking.

**Not selected**: a Cloud SQL or AlloyDB serving projection (revisit on the #23 closing criteria measured end to end through the deployed API in DE-30: more than 5% of requests miss a warm cache, or a shared cache's latency breaks the 200 ms p95; also if a new lookup capability's stated p95 is missed by BigQuery + cache, or an availability target is set that the cache path cannot meet; a mandated relational standard re-scopes #23 as its own decision); Memorystore (revisit if DE-30, with 2 or more instances on real or replayed traffic, measures a steady-state miss share above 5% that one shared key space would bring below 5%, while a measured round trip keeps the p95 at or below 200 ms); BigQuery alone (revisit if a deployed miss-path p95 at or below 200 ms is measured at the stated load, or the API product owner replaces the target or declares the consumer batch); Cloud Run functions, GKE and an API gateway (D10).

**Implemented by**: DE-28 [#149], DE-30 [#151], DE-29 [#150], DE-17 [#138], DE-23 [#144], DE-26 [#147], DE-27 [#148].

**Evidence**: [`service/`](../../src/research_platform/service/) and `test_data_service.py::test_no_raw_sql_consumer_capability`; [data service](../architecture/data-service.md#bigquery-first-intended-backing-logical); [`serving/lookup_cache.py`](../../src/research_platform/serving/lookup_cache.py); [`lookup_cache_measure_118.py`](../../scripts/lookup_cache_measure_118.py); [query routing gate](../architecture/query-routing.md#operational-store-gate). Latency through HTTP, the `research_discovery` miss path and multi-instance hit rate: not yet measured.

### D9 Portability boundary

**Decision**: Following lead §27, these stay **cloud-neutral**: canonical Parquet releases with manifests (D1); PyArrow `CANONICAL_SCHEMAS` and the logical model (entities, relationships, the query-pattern registry, Gold mart grains); the `DataService` contracts and the HTTP API contract (an OpenAPI document with no GCP identifiers); and the seams `ObjectStore`, `Warehouse.query`, `ConsumerDataRepository` and `ControlStore`. These are **GCP-specific internals**: BigQuery SQL, DDL, partitioning, clustering and MERGE (authoritative only in `sql/bigquery/openalex/`); `BigQueryWarehouse` and `GCSObjectStore`; the Cloud SQL control schema; IAM, Workload Identity Federation and Secret Manager; Cloud Run and Workflows configuration; monitoring. Internals never appear in consumer responses, cursors, error messages or the API contract: no project IDs, dataset or table names, bucket names or Cloud Storage paths. DE-31 [#152] analyst-facing BigQuery Gold views and DE-32 [#153] governed BigQuery feature inputs are the two recorded exceptions to §27's "not directly to consumers": GCP-specific channels, not the product API, whose column contracts come from the logical Gold grains and the canonical schemas. They stand only if the lead architect accepts them at sign-off; otherwise consumers use the Data Service or canonical Parquet releases. Release manifests and publication records give consumers relative file paths and logical release ids only (D1), never bucket names or Cloud Storage URLs. Changing the analytical engine means rewriting physical SQL, an accepted cost (register L30-12). The program stays GCP-only; there is no AWS implementation.

**Options considered**: contract-level portability (selected); engine-neutral SQL everywhere (one source transpiled or run through multi-engine adapters); no boundary (BigQuery as the system of record).

**Rationale**: This restates §27 over seams that already exist and are tested offline: the `ObjectStore` contract suite runs on the local and GCS adapters, the `Warehouse.query` adapters exist for DuckDB, PostgreSQL and BigQuery, and `CANONICAL_SCHEMAS` equal the BigQuery contract. It keeps BigQuery SQL single-sourced, which engine-neutral SQL would break, and it keeps the canonical layer independent of any engine (§3.1, §30).

**Consequences**: The known breaches are assigned: the literal `openalex` dataset in all 61 SQL files (D2, DE-13); `export.py` importing `lineage_columns` from `persistence/postgres/row_codec` (DE-07); canonical Parquet that exists only locally (DE-07); Gold and quality logic hand-copied into DuckDB for tests (parity tests in DE-16/DE-17). The documented rule that responses carry no physical storage fields has no direct test; DE-28 adds one. Docs that said "Parquet where (genuinely) applicable" (`README.md`, `gcp-bigquery-first.md`, `roadmap.md`) are aligned with §30 for the canonical layer in the #124 change.

**Not selected**: engine-neutral production SQL (revisit when a second production engine is approved under the Trino or Iceberg trigger in D10); no portability boundary with BigQuery as the system of record (only an ADR revision amending §3.1/§30).

**Implemented by**: DE-07 [#128], DE-13 [#134], DE-28 [#149], DE-31 [#152], DE-32 [#153].

**Evidence**: [`storage/base.py`](../../src/research_platform/storage/base.py); [`warehouse/base.py`](../../src/research_platform/warehouse/base.py); [`service/repository.py`](../../src/research_platform/service/repository.py); [`test_object_store.py`](../../tests/contract/test_object_store.py); [`canonical/openalex/schemas.py`](../../src/research_platform/canonical/openalex/schemas.py). ### D10 Limits on optional technologies

**Decision**: These are **not selected for the first iteration**: Spark on Dataproc, Dataflow, Cloud Batch, BigQuery external tables, BigLake tables, Apache Iceberg or another open table format, Trino, GKE, Cloud Run functions / Cloud Functions, Memorystore, Cloud SQL/AlloyDB and other operational serving stores, API Gateway/Apigee, Vertex AI, and vector or graph engines. Each has a measurable revisit trigger in [Not selected](#not-selected). DE-35 [#156] owns the trigger register and opens a separate, benchmark-backed issue only when a trigger fires; no resource, dependency or infrastructure code is created for any of them. Where a trigger names a refresh window it uses 24 h until the lead architect signs a window from DE-05's cadence; where it names a budget threshold, the budget owner sets it in DE-26. Because `BenchmarkResult` accepts `MEASURED` only for engines named BigQuery, a measured comparison of any alternative first needs a reviewed change to that validator (DE-18/DE-35).

**Options considered**: per technology, adopt now, not select with a measurable trigger (selected), or exclude permanently.

**Rationale**: Lead §28 says such additions are driven by actual requirements and not introduced in the first iteration by default; §29 and §22 add components only on measured need; [#33] already made Spark/Dataproc and Iceberg/BigLake optional; and the program rules forbid adopting a technology because a diagram shows it. The largest measured scale is 100,100 synthetic Works, with BigQuery tables up to 388.4 MiB, and the only scaling signal (local peak RSS in `export_snapshot_to_parquet`) is expected to be addressed by streaming writers and sharding (DE-07, DE-20; not yet built or measured), not by a new engine. AI, ML, knowledge-graph, vector and RAG work is outside DE scope and bound by OpenAlex rights (D12).

**Consequences**: Because canonical data stays Parquet in Cloud Storage, external tables, BigLake/Iceberg, Spark and Trino remain attachable later without re-ingesting OpenAlex, and the #112 prototype keeps a PostgreSQL projection reachable if #23 reopens. DE-35 should add Dataform, dbt and scheduled queries to its conditional list (D7). Thresholds left unset by owners would turn triggers into "never revisit", so DE-35 tracks them as open inputs.

**Not selected**: in short form, with the full triggers in the [Not selected](#not-selected) table (rows marked D10): Spark on Dataproc (a canonical transform unit on real data above 80% of the runtime's task memory or timeout after streaming writers and sharding, or a full rebuild beyond the refresh window); Dataflow (a measured ingest overrunning the freshness window at maximum parallelism, a cross-asset shuffle, or an approved streaming source); external and BigLake tables (load plus publication of one release beyond the refresh window, native storage the largest cost line, a consumer of non-loaded releases, or a mandated policy on Cloud Storage data); Iceberg (a second engine, concurrent canonical writers, an as-of read beyond retained releases, or a schema change that cannot ship as a new version plus rebuild); Trino (an approved second-engine requirement, or a DE-18 pattern missing its agreed target after tuning); GKE and Cloud Functions (an enterprise GKE mandate or a failed Cloud Run acceptance case; event-only glue under 10% of the functions timeout); API Gateway/Apigee (external consumers, API keys or per-consumer quotas); Vertex AI, vector and graph engines (a lead-approved downstream charter with rights clearance and a measured workload BigQuery misses).

**Implemented by**: DE-35 [#156]; measurements from DE-18 [#139], DE-20 [#141], DE-30 [#151].

**Evidence**: [design principles](../architecture/gcp-bigquery-first.md#design-principles); [`benchmarks/models.py`](../../src/research_platform/benchmarks/models.py) and `test_query_pattern_registry.py::test_local_benchmark_result_cannot_claim_measured_bigquery`; [#108 Stage 2 table sizes](../architecture/bigquery-analytical-models.md#recorded-run-108-stage-2). ### D11 Identity and access policy

**Decision**: Deploy and runtime identities are separate in every environment, which closes the single-identity gap of [#108] for direct access; the deploy identity's indirect reach through `actAs` is bounded in (a).

- **(a) Deploy:** one CI deploy identity per environment, reached only through Workload Identity Federation from GitHub Actions OIDC. It holds infrastructure deploy rights (Cloud Run, Workflows and Scheduler definitions, and the buckets, datasets and IAM bindings that DE-23 delivers as infrastructure code), `actAs` granted on each runtime service account individually (never a project-wide Service Account User grant), no database login and no data-plane role: it cannot read or write an object or table data directly. Because `actAs` plus deploy rights let it run code as any runtime identity, and IAM-binding rights let it change grants, it is treated as the most privileged principal of its environment: it deploys only image digests that CI built from the protected default branch, only from that environment's protected GitHub environment with required reviewers, and every IAM policy change raises an alert (D13 (f)). The provider condition matches the immutable `repository_id` and `repository_owner_id` claims, the environment claim and the protected ref, never the repository name alone *(PC: names can be re-registered)*. Deploy workflows never run on `pull_request_target`, `workflow_run` or fork-triggered events, and `id-token: write` is granted only at job level in those deploy jobs (DE-27).
- **(b) Runtime:** one service account per job type, attached to the Cloud Run job or service (WIF is for CI only): Bronze ingest (object create and get on Bronze only; no delete or list, as in #108); canonical publish (create and get on Silver); consumer publication (the pointer compare-and-set through the control plane and create-only publication records in Silver, D1); Silver garbage collection (the only identity with standing object delete, D1; a D12 (d) takedown uses time-bound break-glass impersonation, not a standing grant); control-schema migrator (DDL on the control database only, D4); BigQuery publish (project-level job creation, job listing where needed, data editing only on the datasets it writes, never dataset creation); quality and Gold as the IAM matrix approves; orchestrator and scheduler (invoke only, no data rights); API read-only (job creation and data viewing on published consumer objects only, needed because `BigQueryWarehouse` does not block write statements); control-plane access by IAM database authentication with DML-only grants (D4); monitoring and audit reader.
- **(c) Humans:** only through role groups. Engineers may run governed direct SQL for debugging and exploration in GCP_SANDBOX and DEV, and analysts may query published Gold objects, under per-user quotas and byte caps (lead §16). QA and PROD have no standing human write access. Manual or break-glass work uses time-bound service-account impersonation with Token Creator granted per account (the #108 pattern).
- **(d) Keys:** no service-account keys anywhere, enforced by the org policy that disables key creation.
- **(e) Secrets:** any secret (prefer IAM authentication, so ideally none) lives in Secret Manager and is referenced by name, never in git, configuration, TaskMessage/XCom, logs or issues.
- **(f) Proof:** DE-23 delivers the IAM matrix as infrastructure code plus negative tests that reuse the #108 probes (403 on overwrite, on an out-of-prefix write and on an unauthorized dataset; no dataset creation) and add new ones (the API identity cannot write; the deploy identity holds no direct data-plane role and cannot read an object or a table directly, while its indirect reach through `actAs` is bounded by the controls in (a); the migrator cannot reach data-plane resources; no cross-environment access). No identity names or project IDs are committed.

**Options considered**: one identity that deploys and runs (the #108 status quo); separated identities with WIF for CI (selected); service-account key files in CI secrets or on workstations; GCP-hosted CI (Cloud Build or Cloud Deploy) with an attached deploy identity.

**Rationale**: [#108] proved least-privilege grants, prefix scoping, keyless impersonation and negative probes (GCS smoke 17/17; BigQuery smoke 10/10; the [#103] re-run as the same identity 95/95), but one identity both created the tables and ran the jobs, and the registry keeps `IDENTITY_IAM`, `WORKLOAD_IDENTITY` and `SECRETS` `CLOUD_UNVERIFIED`. The docs already require separate deployment and runtime identities, no service-account JSON keys in the repository and, for now, no cloud deploy credentials stored in GitHub Actions; D11 (d) extends the key rule to every environment. GitHub Actions is the only CI, and *(PC)* WIF attribute conditions limit which repository and environment can obtain tokens.

**Consequences**: The CI workflow today has `contents: read`, `persist-credentials: false`, no `id-token` permission and no cloud credentials; DE-27 adds `id-token: write` only to deploy jobs. The publish identity needs data editing (the floor for `CREATE OR REPLACE TABLE`), so it can rewrite any table in its datasets; published consumer objects therefore sit apart from writable working datasets, so the API identity can be viewer-only. More identities need review, and `actAs` chains need careful scoping: the separation limits direct access, but the deploy identity can still act through any runtime identity, which is why (a) bounds what it may deploy and alerts on IAM changes. Readiness levels do not change.

**Not selected**: one identity for deploy and runtime (allowed only for a time-boxed GCP_SANDBOX smoke run with a Security and governance exception recorded on the issue beforehand; never in DEV, QA or PROD); service-account keys (never; if org policy forbids GitHub OIDC federation, use GCP-hosted CI, not keys); GCP-hosted CI as the primary deploy path (revisit if org policy disallows external workload identity providers, or governance requires deploys to originate inside the organization, recorded in DE-04 or DE-27).

**Implemented by**: DE-23 [#144], DE-27 [#148], DE-04 [#125], DE-24 [#145].

**Evidence**: [IAM, workload identity and secrets](../architecture/environment-readiness.md#iam--workload-identity--secrets); [#108 Stage 1 grants and probes](../architecture/bigquery-analytical-models.md#recorded-run-108-stage-1); [`.github/workflows/tests.yml`](../../.github/workflows/tests.yml); `test_bigquery_warehouse.py::test_logs_do_not_include_secrets_or_sql_payload`. Separated identities in an enterprise project: not yet measured.

### D12 Data and rights policy

**Decision**:

- **(a) Rights:** ingest and publish OpenAlex **metadata only**. No tracked file yet records the OpenAlex licence, terms of use or attribution, or any full-text rights statement; DE-05 records them from OpenAlex's own documentation before any real ingestion. Full article text, including anything reached through `has_fulltext` or location URLs, is out of scope: no download, embedding or model training without a separate written rights approval and its own issue outside the DE program. Abstracts (`abstract_inverted_index`, `DEFERRED` today but present in the Bronze raw bytes) are not added to canonical, BigQuery or served layers, and are never embedded or used for training, until DE-05 records that the OpenAlex terms cover them and the Security and governance owner approves. `pdf_url` and `landing_page_url` are stored only as metadata strings and are never fetched. The primary-location `license` (stored on `work_locations`; canonical `works` has no licence column) describes a work; it grants nothing.
- **(b) Classification (proposed):** this ADR proposes classifying the data as public research metadata that includes researchers' personal data (author `display_name`, `orcid`); the Security and governance owner confirms or replaces this in DE-25 [#146] before DE-05 allows real ingestion. Lineage columns are internal unless DE-25 approves exposing them. Only OpenAlex public metadata and synthetic data are allowed: no Wiley or proprietary data, and no AACT/ClinicalTrials, FDA or news feeds.
- **(c) Retention:** Bronze is immutable and create-only under an unlocked retention policy (period set in DE-24), and no lifecycle rule deletes a raw snapshot that a retained release depends on or that holds source fields Silver does not carry (D1). Keep at least the current and the previous published Silver release plus pinned releases (N set in DE-24), and the publication records of every retained release. Authoritative Silver and Gold BigQuery tables have no table or partition expiration in any environment (D2); only scratch and per-load staging datasets and ephemeral `r_<32 hex>` test datasets use a default table expiration (14-day precedent) and no partition expiration. Soft delete stays at the default window unless DE-24 changes it; no object versioning on create-only prefixes; no locked retention unless a legal WORM requirement is recorded; log retention follows enterprise policy.
- **(d) Deletion precedence:** OpenAlex deletions are tombstones (`activity_state = DELETED`); Work rows are never physically deleted; relationships owned by a deleted Work are preserved (Policy A); consumer models filter ACTIVE; the Data Service returns NOT_FOUND for inactive Works; a newer ACTIVE observation after a tombstone raises `RestoreRequiredError`; unknown-work barriers travel in every release (D1). Storage lifecycle never implements source deletions. A legal or rights takedown is a separate approved, audited procedure run through time-bound break-glass impersonation, recorded on its own issue; it covers Bronze objects, Silver releases and publication records, BigQuery tables, and their soft-delete, time-travel and fail-safe copies *(PC: these copies outlive an ordinary delete for their window)*.
- **(e) Lineage and semantics:** lineage carried in the data (`run_id`, `asset_id`, checksum, publication or release version, `rp_provenance`) stays authoritative. Null versus missing distinctions (the `*_presence` columns), fan-out safety and the primary-location licence semantics are preserved through every layer.
- **(f) Catalog:** datasets, release manifests, owner roles, glossary terms, licensing notes and lineage are registered in Google Cloud's managed catalog (Dataplex Universal Catalog; DE-25's text calls it Knowledge Catalog), with entries generated from repository contracts. Python steps emit explicit lineage events, because *(PC)* automatic lineage covers BigQuery jobs only. If DE-04 names a different enterprise catalog standard, that standard is used.

**Options considered**: this policy (selected); in-repo governance only; the full Dataplex suite (lakes and zones, automatic quality and profiling scans, BigLake governance); age-based lifecycle deletion, object versioning or locked retention; a VPC Service Controls perimeter and CMEK by default; full-text acquisition.

**Rationale**: The metadata versus full-text distinction is non-negotiable and nothing records the OpenAlex terms yet. Deletion semantics are implemented and tested (zero DELETED Works leaked into Gold in every #103-script run, on synthetic data), and lifecycle rules must never break replay or tombstones (§3.1, §18). A generated catalog is the smallest step that meets the catalog capability (register L02-38) without duplicating repository quality SQL (DE-16) or adopting BigLake.

**Consequences**: DE-05 blocks real ingestion until the terms are recorded and the snapshot is sized. Obligations for researchers' personal data are unassessed. Retention without age-based deletion grows storage until DE-24 sets periods. Catalog lineage stays incomplete for Python steps unless they emit events.

**Not selected**: no managed catalog (revisit if DE-04 records that the managed catalog is not approved; the docs site and register then stay the interim catalog, recorded as a DE-25 blocker); Dataplex lakes, zones, automatic quality scans and BigLake governance (revisit if DE-16 records a required gate that repository SQL cannot express, governance mandates object-level policy on Cloud Storage that bucket IAM and BigQuery cannot enforce, or a DE-35 BigLake trigger fires); another enterprise catalog (when governance names a standard); a VPC Service Controls perimeter and CMEK by default (revisit if enterprise policy or the recorded data classification mandates a perimeter or customer-managed keys; DE-24); Bucket Lock, versioning, colder classes and age-based deletion (consolidated table); full-text acquisition, embedding or training (only with a written rights approval for a named source and a separately approved issue outside DE); Vertex AI, vector and graph engines (D10).

**Implemented by**: DE-05 [#126], DE-24 [#145], DE-25 [#146], DE-11 [#132], DE-16 [#137].

**Evidence**: [tombstone semantics](../architecture/openalex-deletions.md#tombstone-semantics); [ACTIVE / deleted semantics](../architecture/data-service.md#active--deleted-semantics); [`field_catalog.py`](../../src/research_platform/canonical/openalex/field_catalog.py) (`has_fulltext` is `SOURCE_ONLY`); [primary-location licence](../architecture/bigquery-analytical-models.md#primary-location-license-behavior); [lineage](../architecture/pipeline-control.md#lineage). A record of the OpenAlex terms: none tracked.

### D13 Observability and cost guardrails

**Decision**:

- **(a) Per-query guard:** keep the fail-closed guard: dry run first, refuse an estimate above `maximum_bytes_billed` (10 GiB default; per-environment values set in DE-26), execute with the cap, time out with cancel; per-run budgets for scripted and runner runs (D7).
- **(b) Labels:** every BigQuery job carries labels for environment, component, `run_id` and publication or release version. `BigQueryWarehouse` sets no job labels today (the [#103] adapter jobs had to be found by time window), so DE-26 adds an optional labels parameter.
- **(c) Quotas:** per-project and per-user BigQuery daily query quotas in GCP_SANDBOX, DEV and QA, and an approved quota in PROD.
- **(d) Budgets and attribution:** a Cloud Billing budget with threshold alerts per project (*(PC)* alerts do not cap spend), billing export to BigQuery, and per-component attribution from labels and job metadata.
- **(e) Pricing model:** on-demand until the capacity trigger fires.
- **(f) SLIs and alerts:** lookup p95 and cache miss share (alert at 5% or more, the #118 rule and the #23 reopen signal); freshness lag against 24 h; pipeline, quality-gate and publication success; bytes billed and slot ms per day per component; source-egress errors; IAM denials; IAM policy changes; secret-access anomalies. Numeric SLO targets beyond the operator-stated 200 ms p95, 5 rps and daily freshness are open inputs for the API product owner.
- **(g) Promotion:** no automatic PROD deploy; promotion requires `can_promote` and human approval. Runbooks for runaway cost and credential expiry come in DE-33.
- **(h) Runtime bounds:** every Cloud Run service sets maximum instances, and every job sets task count and task parallelism limits, per environment in DE-26; the run lease (D6) bounds concurrent executions. API maximum instances also bound cold-cache misses, because each instance warms its own cache (D8).
- Budget amounts, quota values, caps and instance limits are recorded in DE-04/DE-26, not in this public ADR.

**Options considered**: layered guardrails on on-demand pricing (selected); BigQuery capacity reservations from the start; per-query caps only (status quo); an automated hard spend stop.

**Rationale**: The per-query cap is the only working guardrail, and it was verified against real BigQuery: [#92] rejected a 1 KiB cap at dry run and an 8 MiB cap failed with 0 bytes billed; [#103] and every [#108] run rejected a 1 MiB cap with 0 bytes billed. The registry records no budgets, attribution or alerts. Labels, quotas, budgets and billing export close those gaps with product features instead of new platforms, and the #118 rule gives a measurable SLI for the only stated latency target.

**Consequences**: `BigQueryWarehouse` needs a code change for labels. Quotas must be tuned so they do not fail legitimate backfills. *(PC)* Budgets alert after the fact, so quotas and the runtime bounds in (h) are what bound a runaway job or service between alert and response. `COST_CONTROLS` and `OBSERVABILITY` stay `CLOUD_UNVERIFIED` until DE-26 evidence exists.

**Not selected**: capacity reservations (revisit if, for two consecutive months, DE-18/DE-26 data shows an environment's on-demand bytes billed costing more than the slot-hours implied by the same month's measured `total_slot_ms`, or the API product owner sets a concurrency SLO that on-demand cannot meet in a DE-18 load test); per-query caps only (no trigger; superseded by this decision); an automated hard spend stop (*(PC)* disabling billing can stop or remove resources; considered for GCP_SANDBOX only, if its spend exceeds the approved monthly budget in any month despite alerts and quotas).

**Implemented by**: DE-26 [#147], DE-27 [#148], DE-33 [#154], DE-18 [#139], DE-30 [#151].

**Evidence**: [`warehouse/bigquery.py`](../../src/research_platform/warehouse/bigquery.py); [`analytics/bigquery/registry.py`](../../src/research_platform/analytics/bigquery/registry.py) (`DEFAULT_MAXIMUM_BYTES_BILLED`); `test_bigquery_warehouse.py::test_dry_run_then_execute_with_budget_and_parameters`; [cap rejections](../architecture/bigquery-analytical-models.md#recorded-run-92). Budgets, quotas, labels and alerts: none deployed; not yet measured.
